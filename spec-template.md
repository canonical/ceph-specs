# Specification title

## Abstract

Short description of the issue being addressed. Limit this to a couple of
sentences.

## Rationale

Reasons why the specification should be accepted. Explain why the existing
state, if any, is inadequate to address the issue. If possible, include use
cases to help define and explain the goal.

Omit this section (rather than presenting silly reasoning) if there's no good
motivation for the specification, or if it is completely obvious. Note that
lack of motivation is a good reason to reject a specification.

## Specification

Describe in detail the issue being addressed and the proposed way to handle
it, covering the areas involved, in enough detail to allow implementing the
feature. This is *not* an extensive whitepaper that should make sense to
someone unaware of the wider context.

Use subsections to structure the specification. Diagrams, code samples
(fenced code blocks), pseudo-code, tables etc. are welcome.

State open issues; they must be resolved before the specification is
approved.

Keep the spec as brief as possible while getting the point across. There is no
minimum length.

## Further Information

Optional. Describe why particular design decisions were made, alternative
designs that were considered, and related work (e.g. how the issue is handled
in other systems).

May also include links to related specs, code repositories, Jira items spawned
by or required for this spec, or other external information.
